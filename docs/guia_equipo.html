Equipo DWH · Control-M

Guía de Warden

Cómo instalar la herramienta, auditar una malla exportada de Control-M e interpretar los hallazgos. La herramienta solo lee el XML: no se conecta a Control-M ni modifica nada.

Qué es

Warden recibe el XML de un Complete Workspace exportado desde Control-M y construye el grafo completo de dependencias (INCOND, OUTCOND, ON/DOCOND y DOFORCEJOB). Después simula la planificación día a día y responde preguntas como estas:

  • ¿Hay algún job esperando una condición que nadie genera?
  • ¿Algún job depende de otro que no se planifica ese día?
  • Si falla JOB_A, ¿cuántos jobs quedan bloqueados detrás?
  • ¿Qué dependencias externas (GDW-, 1PJ1-, GBI-) son críticas para el batch?

Cada problema se agrupa por causa raíz con su impacto directo e indirecto, para no tener que revisar cientos de alertas repetidas. Si con la información del XML no se puede demostrar un problema, el hallazgo sale como INFO y no como ALTA.

Compartir con el equipo

Lo haces una sola vez, como responsable de la herramienta. Lo más cómodo es un repositorio Git, porque así todo el equipo recibe las mejoras y los cambios de configuración.

  1. Crea el repositorio Desde la carpeta Warden, crea un repositorio en el GitLab, GitHub o Azure DevOps del proyecto y sube el código. No subas los XML ni los informes: pueden contener nombres de servidores y direcciones de correo.
    PowerShell o Git Bash
    cd C:\Users\ochaabay\Downloads\Warden
git init
git add README.md pyproject.toml requirements.txt warden.py config docs src tests input/.gitkeep report/.gitkeep logs/.gitkeep
git commit -m "Warden: primera versión"
git remote add origin <URL_DEL_REPOSITORIO>
git push -u origin main
  2. Añade un .gitignore Así nadie sube por error mallas, informes o logs.
    .gitignore
    input/*
!input/.gitkeep
report/*
!report/.gitkeep
logs/*
!logs/.gitkeep
__pycache__/
.pytest_cache/
  3. Da acceso al equipo Pasa a tus compañeros la URL del repositorio y el enlace a esta guía. Si no tenéis repositorio, una alternativa es comprimir la carpeta en un zip y dejarlo en la unidad compartida del proyecto, aunque así cada uno tendrá que actualizar su copia a mano.

Instalar

Cada persona del equipo lo hace una vez en su equipo. Solo necesita Python 3.10 o superior (en PowerShell, python --version debe mostrar 3.10 o más).

  1. Descarga el código 
    git clone <URL_DEL_REPOSITORIO> Warden
cd Warden
  2. Crea un entorno virtual (recomendado, para no mezclar librerías con otros proyectos)
    PowerShell
    python -m venv .venv
.venv\Scripts\Activate.ps1
    Si PowerShell bloquea el script de activación, ejecuta antes Set-ExecutionPolicy -Scope CurrentUser RemoteSigned.
  3. Instala las dependencias 
    pip install -r requirements.txt
    Son tres librerías: networkx, PyYAML y pytest. Si quieres además el comando Warden, ejecuta también pip install -e .
  4. Comprueba que funciona 
    python -m pytest -q
    Debe terminar con 51 passed.

Ejecutar una auditoría

  1. Exporta la malla desde Control-M En Control-M, abre el Workspace con los folders que quieras auditar y expórtalo como XML. Se recomienda un Complete Workspace con todos los folders relacionados: si falta un folder, sus condiciones aparecerán como «sin productor».
  2. Copia el XML a input/ Si el nombre tiene espacios, ponlo entre comillas al ejecutar.
  3. Lanza la auditoría 
    python warden.py "input/Complete Workspace.xml" --start-date 2026-11-01 --days 365
    Una malla de unos 1.300 jobs tarda un par de segundos. Al terminar, la consola muestra un resumen y las rutas de los ficheros generados.

OpciónPara qué sirve

Varios XMLpython warden.py a.xml b.xml los analiza como una sola malla.

Ficheros que genera

Leer el informe

El HTML funciona sin conexión y se puede enviar por correo. Arriba muestra el resumen (jobs, folders, dependencias y número de hallazgos por severidad). Debajo están los filtros por severidad, regla, folder, application y sub-application, y un buscador de jobs y condiciones. Al abrir un hallazgo se ven la condición, el productor, el consumidor, la planificación, las fechas afectadas, la causa raíz, el impacto, la recomendación y, si aplica, el subgrafo de jobs afectados.

SeveridadSignificadoQué hacer
ALTAEstá demostrado que un job no puede ejecutarse.Revisar y corregir. Empezar por el filtro «Solo causas raíz».
MEDIARiesgo real, pero depende de algo que el XML no muestra (ejecución manual, AND/OR ambiguo, horarios).Revisar con el responsable de la cadena.
BAJAConfiguración mejorable que no bloquea la ejecución.Planificar la limpieza.
INFOContexto: dependencias externas, jobs sin planificar, puntos con muchas dependencias, casos no verificables.Consultar cuando haga falta.

La lista completa de reglas (CTM001 a CTM020) está en el README.md del repositorio.

Configurar reglas

Todo se ajusta en config/controlm_rules.yaml, sin tocar código. Como el fichero está en el repositorio, un cambio confirmado se aplica a todo el equipo.

config/controlm_rules.yaml
external_condition_prefixes:      # condiciones de otros Control-M / sistemas
  - "GDW-"
  - "1PJ1-"
  - "GBI-"
external_conditions:              # externas con nombre exacto
  - "METADATOSCONTROLMJAZZTEL999-TO-EXA_CALCULA_CAMINO_CRITICO"
excluded_jobs: []                 # jobs que no se quieren auditar
excluded_folders: []
simulation:
  new_day_time: "0700"            # hora del New Day (mejora CTM007)
  user_daily_times: {DWH_18: "1800"}
Dependencia externa y exclusión no son lo mismo. Una condición declarada externa deja de ser un error, pero se sigue analizando y se calcula su impacto. Una exclusión la retira de las reglas. Para condiciones que llegan de otro sistema, usa casi siempre external_conditions.

Rutina recomendada

  1. Antes de subir cambios a la malla Exporta el workspace con tus cambios, ejecuta la auditoría y comprueba que no aparecen ALTA nuevas respecto al informe anterior.
  2. Revisión periódica Una vez por semana o tras cada despliegue, una persona del equipo audita el Complete Workspace y deja el HTML en la carpeta compartida.
  3. Cuando un ALTA resulta ser correcto Si la condición la genera otro sistema, añádela a external_conditions y sube el cambio al repositorio, para que deje de aparecer a todo el equipo.

Problemas frecuentes

La consola muestra caracteres raros (Ã³, �)

La consola de Windows no está en UTF-8. Los informes HTML y JSON salen bien de todas formas. Para corregir la consola, ejecuta antes $env:PYTHONIOENCODING="utf-8" en PowerShell.

«No module named networkx» o «No module named yaml»

No está activado el entorno virtual o no se instalaron las dependencias. Repite los pasos 2 y 3 de la instalación.

Muchas condiciones «sin productor»

Probablemente el XML no incluye todos los folders. Exporta el Complete Workspace o pasa varios XML a la vez.

Un hallazgo dice «No verificable con la información disponible»

El XML no permite decidir ese caso (calendarios externos, expresiones como D6W1). La herramienta prefiere marcarlo como INFO antes que dar un falso error, así que hay que revisarlo a mano.
